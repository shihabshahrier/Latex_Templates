% ================= Overview =================
\section*{\color{nexanavy}\Large\bfseries Overview}
\vspace{-2mm}
{\color{softline}\hrule height 0.8pt}
\vspace{2mm}

Nexa Connect is the unified API for payments, identity verification, and ledger
reconciliation used by finance teams building on the Nexa platform. This guide covers
authentication, the core REST endpoints, official SDKs for Python and Node.js, webhook
signature verification, and error-handling conventions. It is written for backend engineers
integrating Nexa Connect into an existing service --- prior familiarity with REST and JSON is
assumed. All requests are made over HTTPS to the single base URL \texttt{https://api.nexa.dev/v2};
there is no per-feature subdomain. Responses are JSON, timestamps are ISO~8601 in UTC, and
monetary amounts are always integer minor units (e.g.\ cents) to avoid floating-point rounding
errors.

% ================= Authentication =================
\section{Authentication}

Every request must carry a bearer API key issued from the Nexa Dashboard under
\textbf{Settings \textrightarrow\ API Keys}. Keys are environment-scoped: a \texttt{test\_}
key never touches production data, and a \texttt{live\_} key cannot be used against the
sandbox host.

\begin{codepanel}{Authenticated request}
\begin{lstlisting}[style=nexabash]
curl https://api.nexa.dev/v2/payments \
  -H "Authorization: Bearer live_9k2Lp7XwQrT4vB1nZcHf" \
  -H "Content-Type: application/json"
\end{lstlisting}
\end{codepanel}

\begin{warnbox}
Do not embed \texttt{live\_} keys in client-side or mobile code. Keys are shown once at
creation time; a lost key must be revoked and reissued, since Nexa does not store the
plaintext value after generation.
\end{warnbox}

\subsection{Key rotation}
\begin{itemize}[itemsep=2pt, topsep=2pt, leftmargin=1.4em]
  \item[\faSync] Rotate keys at least every 180 days; old and new keys overlap for 24 hours.
  \item[\faSync] Revoking a key invalidates it within 30 seconds across all edge regions.
\end{itemize}

% ================= SDK Quickstart =================
\section{SDK Quickstart}

Official SDKs are published for Python and Node.js and wrap retry logic, idempotency-key
generation, and typed response models. Both snippets below perform the same action:
creating a \$42.50 payment for an existing customer.

\begin{minipage}[t]{0.485\textwidth}
\begin{codepanel}{Python -- \texttt{nexa-connect}}
\begin{lstlisting}[style=nexapython]
from nexa_connect import Client

client = Client(api_key="live_9k2Lp7XwQrT4vB1nZcHf")

payment = client.payments.create(
    amount=4250,
    currency="usd",
    customer="cus_82nF3kLp",
    description="Invoice 10432",
    idempotency_key="inv-10432-charge",
)

print(payment.id, payment.status)
\end{lstlisting}
\end{codepanel}
\end{minipage}\hfill
\begin{minipage}[t]{0.485\textwidth}
\begin{codepanel}{Node.js -- \texttt{@nexa/connect}}
\begin{lstlisting}[style=nexajs]
import { NexaConnect } from "@nexa/connect";

const client = new NexaConnect({
  apiKey: "live_9k2Lp7XwQrT4vB1nZcHf",
});

const payment = await client.payments.create({
  amount: 4250,
  currency: "usd",
  customer: "cus_82nF3kLp",
  description: "Invoice 10432",
  idempotencyKey: "inv-10432-charge",
});

console.log(payment.id, payment.status);
\end{lstlisting}
\end{codepanel}
\end{minipage}
\par

\vspace{1mm}
\begin{warnbox}
Always pass an explicit \texttt{idempotency\_key} on payment creation. Without one, a
retried request after a network timeout can create a duplicate charge; both SDKs surface
this parameter directly for that reason.
\end{warnbox}

\section{Response Schema}

A successful \texttt{POST /payments} call returns a \texttt{payment} object. Field names
and types are stable across API versions; new fields may be added but existing ones are
never removed or repurposed within a major version.

\texttt{currency} & string & ISO 4217, lowercase. \\

\subsection{Status values}
\begin{itemize}[itemsep=2pt, topsep=2pt, leftmargin=1.4em]
  \item \texttt{requires\_capture} --- authorized, awaiting the merchant to capture funds.
  \item \texttt{succeeded} --- funds captured and settlement scheduled.
  \item \texttt{failed} --- the issuer or ledger declined the transaction.
  \item \texttt{canceled} --- voided before capture; no funds were moved.
\end{itemize}

% ================= Error Handling =================
\section{Error Handling}

Nexa Connect uses conventional HTTP status codes: \texttt{2xx} for success, \texttt{4xx}
for client-side request errors, and \texttt{5xx} for platform-side failures. Every error
body includes a machine-readable \texttt{code} in addition to the HTTP status, since a
single status like \texttt{402} can map to several distinct \texttt{code} values.

\renewcommand{\arraystretch}{1.15}
\begin{longtable}{@{}>{\centering\arraybackslash}p{1.3cm} p{4.5cm} p{9.2cm}@{}}
\toprule
\textbf{HTTP} & \textbf{code} & \textbf{Meaning} \\
\midrule
\endfirsthead
\toprule
\textbf{HTTP} & \textbf{code} & \textbf{Meaning} \\
\midrule
\endhead
400 & \texttt{invalid\_request} & A required field was missing or malformed. \\
401 & \texttt{invalid\_api\_key} & The bearer key is missing, revoked, or from the wrong environment. \\
402 & \texttt{card\_declined} & The issuer declined authorization; safe to retry with a different instrument. \\
402 & \texttt{insufficient\_funds} & Declined specifically for balance; do not silently retry. \\
404 & \texttt{resource\_missing} & The referenced ID does not exist in this environment. \\
409 & \texttt{idempotency\_conflict} & Same idempotency key reused with different parameters. \\
429 & \texttt{rate\_limited} & Too many requests; back off per the \texttt{Retry-After} header. \\
500 & \texttt{internal\_error} & Unexpected platform fault; safe to retry with backoff. \\
\bottomrule
\end{longtable}

\vspace{1mm}
\begin{codepanel}{Error response shape}
\begin{lstlisting}[style=nexajson]
{
  "error": {
    "code": "card_declined",
    "message": "The card was declined by the issuing bank.",
    "request_id": "req_3Lm8pQxV2n"
  }
}
\end{lstlisting}
\end{codepanel}

\begin{infobox}
Always log \texttt{request\_id} alongside application errors. Support cannot look up a
failed call without it, since request bodies are not retained beyond 72 hours.
\end{infobox}

% ================= Webhooks =================
\section{Webhooks}

Register an HTTPS endpoint under \texttt{/webhooks/endpoints} to receive asynchronous
events --- settlement, chargebacks, and payouts all arrive this way instead of through
polling. Every delivery is signed with HMAC-SHA256 so the endpoint can verify it
genuinely originated from Nexa.

\begin{codepanel}{Verifying the signature (Node.js)}
\begin{lstlisting}[style=nexajs]
import crypto from "crypto";

function verifySignature(rawBody, header, secret) {
  const [tPart, sigPart] = header.split(",");
  const timestamp = tPart.split("=")[1];
  const signature = sigPart.split("=")[1];

  const expected = crypto
    .createHmac("sha256", secret)
    .update(`${timestamp}.${rawBody}`)
    .digest("hex");

  return crypto.timingSafeEqual(
    Buffer.from(expected),
    Buffer.from(signature)
  );
}
\end{lstlisting}
\end{codepanel}

\subsection{Key event types}
\begin{minipage}[t]{0.5\textwidth}
\begin{itemize}[itemsep=1.5pt, topsep=1.5pt, leftmargin=1.4em]
  \item \texttt{payment.succeeded} --- capture completes, funds scheduled for settlement.
  \item \texttt{payment.failed} --- an authorization or capture attempt is declined.
\end{itemize}
\end{minipage}%
\begin{minipage}[t]{0.5\textwidth}
\begin{itemize}[itemsep=1.5pt, topsep=1.5pt, leftmargin=1.4em]
  \item \texttt{payout.paid} --- a scheduled payout to the merchant's bank clears.
  \item \texttt{chargeback.opened} --- a cardholder disputes a settled payment.
\end{itemize}
\end{minipage}
\par

\begin{warnbox}
Respond to webhook deliveries with a \texttt{2xx} within 10 seconds. Nexa retries
undelivered events with exponential backoff for 72 hours, then marks the event as
permanently failed and surfaces it in the dashboard's delivery log.
\end{warnbox}

\subsection{Rate limits \& pagination}

Rate limits are enforced per API key on a rolling 60-second window; usage is always
returned on every response via headers, so clients need no separate endpoint to check
remaining quota. \texttt{X-RateLimit-Limit} and \texttt{X-RateLimit-Remaining} report the
window totals, and a \texttt{429} response adds \texttt{Retry-After} with the seconds to
wait before retrying. Bulk operations (customer imports, ledger exports) should use
\texttt{/ledger/entries} cursor pagination rather than requesting a higher ceiling ---
600/min is rarely the real bottleneck once paging is implemented.
